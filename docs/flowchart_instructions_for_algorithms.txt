Рекомендации по построению блок-схем для двух ключевых алгоритмов

Ниже приведены пояснения, как оформить блок-схемы для двух выбранных алгоритмов: поиска сотрудников (DataManager::findEmployees) и отмены последнего действия (DataManager::undoLastAction). Стиль оформления можно взять по аналогии с примерами из курсовой по кинотеатру: овалы для начала/конца, прямоугольники для действий, ромбы для проверок условий, многоугольники для циклов.

1. Общие правила построения блок-схем

• В верхней части схемы разместить блок «Начало» (овальная форма).
• Все действия (чтение данных, изменение переменных, вызовы методов) отображать прямоугольниками с коротким, но понятным текстом.
• Любое ветвление по условию изображать ромбом с вопросом внутри и двумя выходами: «да» и «нет» (как на предоставленных образцах).
• Циклы «пройти по всем элементам» оформлять либо явно, как блок «i от 1 до N» (многоугольник), либо через комбинацию из действия, условия и обратной стрелки, как это сделано на схемах updateTickets и buyTicket.
• Внизу схемы разместить блок «Конец» (овальная форма).
• Стрелки должны однозначно показывать порядок выполнения шагов; текст «да/нет» располагать рядом с ветвями от ромба.

2. Блок-схема для алгоритма DataManager::findEmployees

При построении схемы алгоритма поиска сотрудников рекомендуется включить следующие ключевые блоки:
• Начало.
• Прямоугольник: «Чтение значений фильтра из интерфейса».
• Прямоугольник: «Формирование структуры EmployeeSearchFilter и установка флагов use*».
• Прямоугольник (многоугольник цикла): «Перебор всех записей из employees».
• Ромб: «Активен фильтр по отделу?». Из него:
  – Ветка «да» → ромб «departmentId сотрудника совпадает с filter.departmentId?», при «нет» — переход к концу цикла (следующий сотрудник).
  – Ветка «нет» — переход к следующей проверке без изменения.
• Аналогичные пары ромбов для минимальной и максимальной зарплаты: проверки useMinSalary/useMaxSalary и сравнений с salary.
• Ромб для фильтра по должности: «usePositionId == true?». При «да» — действие «Пробуем привести employee к Worker» и ромб «Приведение успешно и positionId совпадает?». При «нет» — переход к следующему сотруднику.
• Ромб для фильтра по фрагменту имени: «useNameFragment == true?». При «да» — действие «Получить getFullName() и найти подстроку», затем ромб «Фрагмент найден?». При «нет» — переход к следующему сотруднику.
• Прямоугольник: «Добавить запись в result», если все проверки пройдены.
• Блок «Конец цикла по сотрудникам».
• Прямоугольник: «Возвратить вектор result».
• Конец.

Важно, чтобы на схеме были видны именно проверки активных флагов фильтра и последовательность их применения, а также цикл по коллекции сотрудников. Текст в блоках должен быть кратким, но повторять формулировки шагов алгоритма.

3. Блок-схема для алгоритма DataManager::undoLastAction

Схема для функции отмены последнего действия проще и должна быть компактной (по аналогии с правой частью схемы updateTickets):
• Начало.
• Ромб: «Стек undoStack пуст?».
  – Ветка «да» → прямоугольник «Вернуть false (отменять нечего)» → Конец.
  – Ветка «нет» → переход к следующему действию.
• Прямоугольник: «Взять верхнюю команду UndoCommand из undoStack и удалить ее из стека».
• Прямоугольник: «Установить undoInProgress = true».
• Прямоугольник: «Вызвать команду undo() (восстановить данные)».
• Прямоугольник: «Установить undoInProgress = false».
• Прямоугольник: «Сохранить/обновить описание последнего отмененного действия».
• Прямоугольник: «Вернуть true».
• Конец.

При желании можно дополнительно показать, что undo() может включать разные типы операций (добавление/удаление сотрудника, изменение параметров), но в основной блок-схеме достаточно одного прямоугольника «Выполнить undo()».

4. Связь текстового описания и блок-схемы

При оформлении пояснительной записки важно, чтобы формулировки шагов алгоритма (см. отдельный файл с пошаговым описанием) совпадали по смыслу с надписями на блок-схеме. Рекомендуется:
• нумерацию шагов в тексте (Шаг 1, Шаг 2, …) соотнести с основными действиями и проверками на схеме;
• использовать те же имена методов и структур (DataManager::findEmployees, EmployeeSearchFilter, undoStack, undoInProgress), что и в исходном коде;
• оформлять схемы в одном стиле с примерами из pdf-файла: одинаковая толщина линий, формы блоков и подписи «да/нет» у ветвлений.

Соблюдение этих рекомендаций позволит легко сопоставить программную реализацию, текстовое описание алгоритмов и их графическое представление в виде блок-схем.
